# gg.bet live monitor

Обновление исследования Polymarket от 17 сентября: [RESEARCH.md](RESEARCH.md).
Там запуск непрерывного журнала стаканов, экспорт сырых событий и план проверки
логики лимитных заявок. Стаканы: `npm run pm`; во втором терминале подписанные заявки: `npm run pm:orders`.

Монитор лайв-счёта и коэффициентов на gg.bet: CS2, League of Legends, Dota 2,
Valorant, теннис и настольный теннис.

## Как устроен сайт

Страница не отдаёт данные в HTML — всё приезжает по **двум GraphQL-вебсокетам**:

| Поток | Что отдаёт |
|---|---|
| `wss://gg-b-gql.gg.bet/graphql` | линия, рынки, коэффициенты |
| `wss://score-board.databet.cloud/graphql` | детальное состояние матча: карта, раунд, бомба, таймер |

HTTP-запросы к `gg.bet/graphql` — только конфиги, локали и баннеры; матчей там нет.

Оба сокета говорят в конверте `subscriptions-transport-ws`:

```json
{ "id": "3", "type": "data", "payload": { "data": { "onUpdateSportEvent": { ... } } } }
```

Полезные поля внутри `data`:

| Поле | Смысл |
|---|---|
| `matches.sportEvents` | полный снапшот линии, приходит один раз при подписке |
| `onUpdateSportEvent` | инкрементальный патч: счёт и коэффициенты |
| `onUpdateSportEventOverviews.replace` | состояние матча от databet |

**Главная тонкость.** В патчах `onUpdateSportEvent` у команд есть только `id`,
без названий — имена приходят один раз в снапшоте. Поэтому патчи имеют смысл
только вместе со снапшотом, и `MatchStore` их сливает.

**Связка потоков.** Id матча у gg.bet выглядит как `5:dbe576ca-…`, у databet —
`dbe576ca-…`, без префикса провайдера. Отсюда `normalizeId()`.

## Виды спорта

Каждый вид спорта — отдельная страница со своими подписками, поэтому монитор
открывает по вкладке на каждый и сливает всё в одно хранилище.

| Ключ | sportId | Название |
|---|---|---|
| `cs` | `esports_counter_strike` | Counter-Strike |
| `lol` | `esports_league_of_legends` | League of Legends |
| `dota` | `esports_dota_2` | Dota 2 |
| `valorant` | `esports_valorant` | Valorant |
| `tennis` | `tennis` | Теннис |
| `table_tennis` | `table_tennis` | Настольный теннис |

Идентификаторы взяты не наугад, а из ответа `categorizerSportList` в
`samples/0021-ws.json`. Любой другой `sportId` тоже можно передать напрямую.

```bash
npm run watch                                  # все пять дисциплин
node src/monitor.mjs --sport cs,tennis         # только выбранные
node src/monitor.mjs --sport all               # включая настольный теннис
```

По умолчанию собираются **CS, Dota, LoL, Valorant и теннис** — те же дисциплины,
что отслеживаются на Polymarket. Раньше дефолтом был один Counter-Strike, и
запуск без `--sport` молча собирал пятую часть.

## Два файла на выходе

`odds-history.csv` отвечает на вопрос «какая была цена в момент T» — строка на
каждое изменение коэффициента:

```csv
ts,sport,match_id,title,score,segment,segment_score,market,selection,price,is_active
```

`changes.csv` отвечает на другой вопрос — «что происходило» — и складывает все
события матча в один упорядоченный поток:

```csv
seq,ts,sport,match_id,title,kind,target,from,to
1,"2026-08-23T19:09:11Z","esports_counter_strike","c5715a56…","Fokus vs BakS","score","","0:0","1:0"
2,"2026-08-23T19:09:26Z","esports_counter_strike","c5715a56…","Fokus vs BakS","price","Победитель / Fokus","1.82","1.81"
```

### Когда именно пишется

В момент прихода кадра, а не по таймеру отрисовки. `--interval` управляет
только тем, как часто перерисовывается консоль; в файлы всё уходит сразу из
обработчика вебсокета, и `ts` — это время получения кадра.

Отсюда практическое следствие: если коэффициент за интервал сходил
`1.82 → 1.85 → 1.81`, на экране будет только `1.81`, а в логе — все три записи.
Консоль показывает состояние, лог хранит историю.

Записи в один файл выстроены в очередь (`src/appender.mjs`). Кадры приходят
чаще, чем завершается запись, и без очереди два параллельных `appendFile`
могут лечь в файл в обратном порядке. Колонка `seq` разводит ещё и события,
попавшие в одну миллисекунду.

Виды событий:

| `kind` | Когда пишется |
|---|---|
| `match_start` | матч появился и стало известно, кто играет |
| `score` | изменился счёт по картам/сетам |
| `segment`, `segment_name` | сменилась карта или сет |
| `segment_score` | счёт внутри карты/сета: раунды, геймы, киллы |
| `round` | сменился раунд (только CS2) |
| `state` | сменилось состояние (`freeze_time`, `live_time`, …) |
| `bet_stop` | приём ставок остановлен или возобновлён |
| `price` | сдвинулся коэффициент |
| `odd_suspended`, `odd_resumed` | исход сняли с продажи или вернули |
| `market_open`, `market_closed` | рынок появился или пропал |

## Разбор нового поля

1. `npm run discover` — снять свежие кадры
2. `npm run inspect` — найти файл с нужными данными
3. `node src/inspect.mjs <файл>` — посмотреть скелет структуры

5. `npm test` — убедиться, что старые записи всё ещё разбираются

## Полнота списка матчей

Лайв-список отдаётся **страницами**: снапшот сообщает общее число матчей в поле
`matches.count`, а событий присылает только первую порцию — остальные
подгружаются при прокрутке. В записанном захвате это видно прямо:

```
count=28   sportEvents=12    (теннис)
count=4    sportEvents=4     (Dota)
```

Пока поле `count` игнорировалось, сборщик молча смотрел только голову списка, и
крупный матч, оказавшийся ниже, не попадал в подписку вообще.

Теперь монитор прокручивает страницу, пока число матчей не сойдётся с
заявленным, и повторяет прокрутку раз в `--rescan` секунд — матчи начинаются в
течение суток и появляются в списке позже. Недобор выводится в шапке:

```
gg.bet · live · 15:41:36
missing: Теннис 12/28  — list not fully loaded
```

Если список упёрся и не растёт, в stderr идёт `list stalled at 12/28`. Молча
недосчитывать матчи он больше не может.

## Состояние матча по видам спорта

Счёт, турнир, команды и коэффициенты приходят из общего `fixture` и одинаковы
везде. А детальное состояние даёт databet, и у каждого вида спорта свой тип:

| Тип | Спорт | Что в строке состояния |
|---|---|---|
| `CSGOOverview` | CS2 | карта, её название, счёт раундов, номер раунда, `BOMB`, формат |
| `LOLOverview` | LoL | карта, счёт по киллам, разница в золоте |
| `Dota2Overview` | Dota 2 | то же плюс сторона (radiant/dire) |
| `TennisOverview` | Теннис | сет, счёт по геймам, очко (`40:AD`), кто подаёт, тай-брейк |

Все четыре разобраны в `src/overview.mjs` и сведены к общим полям — `segmentKind`
(карта или сет), `segmentNo`, `segmentScore`, `round`, `state`, `extra`. Поэтому
хранилище, отрисовка и журнал изменений про виды спорта ничего не знают.

Как это выглядит:

```
Just Players vs ex-Zero Tenacity   1:0
  map 2/3 · de_nuke · 6:11 · round 17 · after_end_time · MR12_OT3

Klim Sani4 vs Team Lynx   0:0
  map 1/3 · 9:8 · live · gold +5902 · home dire

Matthew Donald vs Хассан, Беньямин   0:1
  set 2 · 0:1 · 40:AD · serve home
```

Вид спорта, которого мы ещё не видели, не ломает разбор: `summarizeOverview()`
падает на общий разбор и достаёт из него столько, сколько получится.

# Polymarket: сборщик стакана

Отдельный процесс рядом со сборщиком gg.bet. Тот трогать нельзя — он крутит
браузер, который падает и перезапускается, а дыра в логе стакана это дыра в
знаменателе fill rate. Общий конфиг, разные процессы.

```bash
npm run pm:markets     # что сейчас проходит фильтр
npm run pm             # сбор: обнаружение + стакан
node src/pm/collector.mjs --once   # один цикл обнаружения и выход
```

Только чтение: ни ключей, ни подписи ордеров.

## Что выяснилось про Gamma API

Проверено на живых ответах, расходится с документацией:

| Ожидание | Реальность |
|---|---|
| `limit=500` за запрос | страница режется до **100**, нужна пагинация по `offset` |
| `eventSlug` в рынке | поля нет, слаг лежит в `events[0].slug` |
| `clobTokenIds`, `outcomes` — массивы | это **JSON-строки**, нужен parse |
| минимальный ордер $1 | `orderMinSize` per-market, на выборке CS2 везде **5** |
| тик 0.001 | тик **per-market**: 58 рынков CS2 с 0.01 и 7 с 0.001 |
| `endDate` — конец матча | **дедлайн резолюции**: `game + 6ч` у CS2, `game + 168ч` у ITF |
| `startDate` — начало матча | момент, когда рынок начал принимать ордера |
| `gameStartTime` в ISO | `2026-09-01 07:30:00+00`: пробел вместо `T`, смещение `+00` |
| offset-пагинация стабильна | ключ сортировки не уникален, страницы повторяются |

Три последние строки стоили проекта пяти дней сбора, см. ниже.

### Время матча

Единственное поле, которое датирует игру, — `gameStartTime`. Оно есть у всех
рынков отслеживаемых дисциплин, но приходит не в ISO (`parseTimestamp` в
`src/pm/schedule.mjs`). `startDate` — это когда рынок открыли для торгов, а
`endDate` — когда он обязан разрешиться; замер по живому API:

| дисциплина | `game − start`, медиана | `end − game`, медиана |
|---|---|---|
| itf | +11.2 ч | **+168.0 ч** |
| cs2 | −2.8 ч | **+6.0 ч** |

Отрицательное значение у cs2 — не ошибка: рынки на поздние карты создаются уже
по ходу матча.

### Нестабильная пагинация

`order=startDate&ascending=false` сортирует по неуникальному ключу: Polymarket
создаёт рынки пачками, и тысяча рынков может иметь один и тот же `startDate` до
секунды. Offset-пагинация по такому ключу повторяет уже выданные строки и
пропускает другие — 20 страниц по 100 дали 1119 уникальных рынков, шесть
страниц не добавили ни одной новой. Обход поэтому останавливается, когда
страница не принесла ничего нового, а пропущенное подбирается на следующих
кругах: расписание подписки накапливается и ничего не теряет.

Последнее важно для порога свипа: три тика на рынке с шагом 0.01 — это 0.03,
реальный обвал, а на рынке с шагом 0.001 — 0.003, то есть шум. Поэтому правило
считается в тиках самого рынка, с абсолютным полом `bidDropMin`.

## Отбор рынков

Дисциплина берётся из **префикса слага события** (`cs2-sangal-psna-2026-08-26`),
а не из текста вопроса: у гандикапов и тоталов вида `Games Total: O/U 2.5`
дисциплины в вопросе нет вообще.

Классификация по двум независимым осям:

- **level** — `segment` (внутри карты/сета) или `match` (весь матч);
- **kind** — `winner`, `handicap`, `total`.

`Map 3 Total Rounds: O/U 24.5` и `Games Total: O/U 2.5` оба тоталы, но на разных
уровнях, и именно это различие и исследуется. Префиксы без сопоставления
считаются и показываются: `node src/pm/markets.mjs --unknown`.

Обнаружение сортирует по `startDate` убыванию — подрынки внутри матча живут
только вокруг матча, поэтому самые новые рынки и есть живые.

## Окно подписки

Обнаружение и подписка — разные вещи, и путать их дорого. Первые пять дней
сбора реестр был зеркалом текущей страницы Gamma: рынок подписывался, попав в
первые 1200 по `startDate desc`, и отписывался, когда его оттуда вытесняли
более новые. Время жизни в этом окне равно `1200 / скорость создания рынков` —
на замере по живому API страница глубиной 1200 покрывала 34 минуты, на том
прогоне вышел час. Рынки же создаются за 11–15 часов до игры. Итог: каждый
рынок наблюдался около часа сразу после создания, матч играли примерно через
сутки, и ни один филл целевых кошельков не попал внутрь наблюдавшегося окна.

Теперь discovery только добавляет рынки в расписание (`src/pm/schedule.mjs`), а
окно считает часы:

- **подписка** при `now >= game_start − leadMinutes` (по умолчанию 10 минут),
  или сразу, если рынок обнаружен уже после этого момента;
- **отписка** при `closed=true` по данным CLOB, либо при
  `now > game_start + holdHours[дисциплина]` как страховка;
- пока рынок в подписке, его не снимают ни по тишине в стакане, ни по тому,
  что Gamma перестала его показывать.

Рынок без `gameStartTime` датируется по `endDate` минус типичная длительность
дисциплины, и только если получившееся начало не дальше `maxAheadHours`; иначе
он не подписывается вовсе, а причина уходит в журнал `universe`.

Расписание держится в памяти, но переживает перезапуск: при старте коллектор
читает последние дневные базы и возвращает в расписание рынки, чья игра ещё не
прошла. Без этого рестарт терял бы всё запланированное на остаток суток —
Gamma показывает рынок около часа после создания и больше не отдаёт его.

Самопроверка — колонка `observed_during_game` в `markets`: были ли снапшоты
книги внутри интервала игры. Она взводится живьём, видна в `markets.csv` и
проверяется в `check.py` секцией `== the subscription window ==`.

## Протокол CLOB WebSocket

Записан в `samples-pm/ws-frames.json`:

- первый кадр после подписки — **массив** снапшотов `book`, дальше идут
  одиночные **объекты**;
- `book` — полная замена, приходит периодически и ресинхронизирует состояние;
- `price_change` несёт `{asset_id, price, size, side}`, где `size` — **новый
  размер на уровне**, а не дельта; ноль убирает уровень;
- `last_trade_price` — принт сделки, к книге отношения не имеет.

## Хранилище

SQLite через `node:sqlite` — встроен в Node 22, поэтому у сборщика **нет ни одной
новой зависимости**. По файлу на UTC-сутки (`data/pm-2026-08-25.sqlite`), запись
пачками в транзакции: коммит на строку ушёл бы весь в fsync.

Таблицы: `markets`, `book`, `sweeps`, `joined`, `wallets`, `gaps`.
В `book` колонка `trigger` — `book` / `change` / `heartbeat`: по ней считается
покрытие и отделяются реальные события от таймерных.

## Сшивка с gg.bet

Общего идентификатора нет, поэтому связка это три условия сразу: похожая пара
команд, окно ±6 часов вокруг **начала матча** и **тот же вопрос на том же
сегменте**. Последнее не опционально: спарить `Map 2 Winner` с победителем
матча означает молча сравнивать разные вопросы и испортить все цифры
расхождения. Окно раньше отсчитывалось от `endDate`, то есть от дедлайна
резолюции — на шесть часов позже игры у CS2 и на неделю у тенниса, — и это
само по себе выбрасывало правильные пары.

Стороны называют сегменты по-разному — Polymarket количественно (`Map 2
Winner`), gg.bet порядковым числительным (`2-й Сет Победитель`) или после
существительного (`Карта 1 - тотал раундов`). Разбираются обе формы.

Отдельно ловится `2-й Сет - Победитель гейма`: победитель гейма внутри сета —
это не победитель сета, и матчиться на `Set 2 Winner` он не должен.

**Единица счёта — третья ось, наравне с уровнем и типом.** `Set Handicap` и
`Фора по Геймам` оба матчевые форы, но одна в сетах, а другая в геймах; `Total
Sets O/U 2.5` и `Тотал геймов` оба матчевые тоталы, но считают разное. Такая
пара даёт не «слегка неточное» расхождение, а ответ на другой вопрос — ровно та
поломка, от которой защищает сверка сегмента, только на одну ось в сторону.
Именно так в прошлом экспорте единственная заполненная строка свипа оказалась
тоталом убийств против тотала раундов. Единица берётся из названия (`kill`,
`round`, `game`, `set`, `map`, последнее упоминание выигрывает: «Карта 1 - тотал
раундов» считает раунды) и сверяется, **только если названа обеими сторонами**:
`Match O/U 23.5` единицу не называет и должен по-прежнему вставать в пару с
`Тотал геймов`. У победителей единицы нет — считать там нечего.

`odds-history.csv` читается хвостом по байтовому смещению — файл append-only,
сборщик gg.bet при этом не трогается вообще. Из пары коэффициентов считается
девигованная вероятность, а возраст последней строки по рынку и есть
`seconds_since_ggbet_quote`.

**Направление.** У рынка Polymarket два токена, и fair одного — дополнение
другого. Сопоставление идёт **по именам исходов**, а не по порядку: если
площадки перечислили команды в разном порядке, выравнивание по позиции
перевернуло бы fair молча и испортило каждую строку `joined`. Over/Under
сопоставляется по словам (`Больше`/`Меньше`), причём по первому токену, а не
регуляркой — `\b` в JavaScript работает только по ASCII и после кириллицы
границы слова не находит.

**Имена команд.** Одной пары имён на рынок мало. Polymarket пишет участников
winner-рынка в `outcomes`, и там фамилии — `Set 2 Winner: Yamaguchi vs Back`
против `W75 Tianjin: Mei Yamaguchi vs Dayeon Back` у gg.bet. По биграммам такая
пара даёт 0.67 при пороге 0.7 и отбрасывается, тогда как тоталы того же матча
берут имена из заголовка события и матчатся на 1.0. Отсюда получался маппинг,
целиком состоящий из тоталов и фор, — ровно тех подрынков, где целевые кошельки
не торгуют.

Поэтому у каждого участника собирается набор имён: из `outcomes`, из вопроса и
из заголовка события. Порядок в разных источниках не совпадает
(`Astakhova vs Naito` в вопросе против `Yuki Naito vs Darya Astakhova` в
заголовке), поэтому каждая следующая пара разворачивается **по именам**, а не
по позиции, и при неоднозначности отбрасывается. К биграммам добавлены два
правила:

- **общая фамилия** — последний токен обязан совпадать, иначе `MOUZ` и
  `MOUZ NXT` слились бы в одну команду;
- **префиксная аббревиатура** — `NAVI` собирается из начал слов
  `Natus Vincere`; каждое слово обязано дать хотя бы букву, и короче трёх букв
  правило не применяется.

`mapping.csv` всё равно правится руками, и строка с `verified=1` не
переписывается автоматикой никогда. Колонки `pm_level` и `pm_kind` показывают,
что таблица на самом деле связала.

## Кошельки

`data-api /activity` раз в 25 секунд по адресам из конфига. У записей нет
идентификатора, поэтому он собирается из `transactionHash + asset + side +
size + price` — одна транзакция может нести несколько филлов. Потолок
пагинации около 5500 записей, поэтому модуль пишет только форвардный поток и
на бэкфилл не годится.

## Роль мейкер/тейкер

У записей о сделках нет флага роли. Единственный способ восстановить её через
API: `takerOnly=true` возвращает строгое подмножество `takerOnly=false`, и
разница — это пассивно исполненные ордера. Проверено живьём на рынке
`0x3c9b7d57`: 124 тейкерских записи внутри 367 всего, и целевой кошелёк
встречается только среди 243 мейкерских, покупая 200 по 0.02.

Это важно, потому что пассивный филл на один-два цента и есть стратегия, а та
же сделка, взятая агрессивно, — её противоположность; в ленте активности они
неразличимы.

Опрос идёт только по рынкам, где засветились целевые кошельки: роль стоит двух
запросов на рынок, и смысл в ней есть там, где есть что размечать.

## Анализатор

```bash
python3 analyze.py --db data --since 2026-08-25
```

Только стандартная библиотека — ни pandas, ни venv.

**Про fill rate.** Считаются рынко-часы, в которых книгу **проели** до порога,
а не те, где лучший бид просто оказался ниже порога. Это разные вещи: книга,
открывшаяся с бидом на 1¢ и не двигавшаяся, возможностью не является — очередь
на этом уровне уже стоит, и ордер встанет за ней. Обе цифры печатаются
раздельно.

## Пороги детектора свипов

Первые сутки реального сбора дали **617 281 срабатывание** — то есть детектор
ловил не обвалы, а шум. Три причины, все закрыты тестами:

- тонкие книги моргают пустотой, когда маркет-мейкер переставляет котировки: при
  пустой книге «съеденными» считались все уровни, хотя есть там было нечего;
- у книги, уже стоящей на центе, обваливаться нечему — движение с 3¢ на 1¢ не то
  событие, которое изучается;
- один настоящий обвал приходит пачкой апдейтов и логировался на каждом.

Добавлены `minBidBefore`, `minSizeConsumed`, `minDepth` и `cooldownSeconds` —
всё в `pm.config.json`.

Отдельно: значимость применяется **на анализе**, а не при сборе. Сырой лог
остаётся полным (обвал, не дошедший до цента, — это знаменатель fill rate), а
фильтр `--min-bid-before` / `--min-consumed` можно перекрутить, не пересобирая
данные. `analyze.py` печатает обе цифры и разбивку по правилам.

## Полнота выгрузки

**Пагинация.** Первая страница — не журнал. `/trades` листается по 500 с
`offset`, `/activity` — до потолка примерно в 5500 записей, о который
эндпоинт упирается. Обрезка не молчит: `truncated` у торгов и `ceiling` у
активности говорят, что посчитанное по ним имеет короткий знаменатель.

Обе прогулки останавливаются, если страница не принесла ни одной новой записи.
Молча проигнорированный `offset` вернул бы одну и ту же страницу бесконечно —
та же поломка, из-за которой опасен фильтр `condition_id` у Gamma.

**Доля тейкеров — измерение, а не вывод.** `takerShare` считается и пишется,
даже когда он равен нулю. «Здесь нет тейкерских сделок» и «мы сюда не смотрели»
— разные утверждения, и второе не должно выглядеть как первое.

**Журнал вселенной.** `universe` пишет каждый рынок, который сборщик
рассмотрел, с причиной, по которой он не был взят: неизвестная дисциплина,
выключенный стакан, не два токена. Без него пустая клетка в распределении
неотличима от неотсмотренной. Журнал идёт только вперёд — что было до его
появления, восстановить нельзя.

## Резолюция рынков и PnL

```bash
node src/pm/resolve.mjs --from target-fills.csv   # кто выиграл + метаданные
python3 analyze_fills.py                          # PnL по позициям
```

Большинство позиций никогда не продаётся. Без исхода рынка нельзя отличить
«сгорела в ноль» от «додержана до резолюции и погашена по доллару», а считать
доходность по одним проданным — ошибка выжившего, которая покажет прибыльной
любую стратегию.

Источник — `GET https://clob.polymarket.com/markets/{condition_id}`: он
принимает id в пути и промахнуться не может. У Gamma фильтр по `condition_id`
игнорируется без ошибки и возвращает нефильтрованный список — тихое отравление
данных.

`pm-resolutions.csv` сам себе кэш: закрытый рынок больше не перезапрашивается,
незакрытый перечитывается на следующем прогоне. Пауза 400 мс, ретраи с
бэкоффом.

Заодно оттуда восстанавливаются `question / sport / market_level`, которых нет
в выгрузке по рынкам, закрывшимся до начала сбора. Правила разбора берутся из
того же `classify.mjs`, что и у сборщика, — не вторая копия на другом языке.

### Что смотрим против того, что умеем назвать

`disciplines` управляет **подпиской** сборщика, `labels` — только именованием.
Кошельки торгуют бейсболом и политикой; чтобы назвать такую позицию в отчёте,
не нужно начинать писать по ней стакан.

### Пять режимов выхода, а не два

Позиция, проданная частично и досидевшая до резолюции, — ни `sold`, ни `held`:
у неё есть и выручка, и погашение. Свалить её в любую из групп значит испортить
и хит-рейт, и кратности этой группы. Поэтому: `sold`, `partial_won`,
`partial_lost`, `held_won`, `held_lost`, а нерезолвленные исключаются явным
числом, а не молча.

PnL печатается ещё и с разделением по цене входа: стратегия входит по 1–2¢, а
позиции, открытые около доллара, — другая активность, и в общей сумме они
маскируют друг друга.

## Проверка сбора

```bash
python3 check.py
```

Проходит по обеим половинам — котировкам gg.bet и стакану Polymarket — и
называет, чего не хватает, вместо того чтобы это всплыло посреди анализа.
Проверяет: все ли пять дисциплин пишутся, сколько рынко-часов покрыто
heartbeat'ами, сколько было разрывов, что видел журнал вселенной и почему
пропускал, правдоподобно ли число свипов, есть ли резолюции по торгованным
рынкам и полон ли `export.zip`.

Итог одной строкой: `15 ok, 8 warnings, 0 missing`. Строки `MISS` означают,
что чего-то обязательного нет; `warn` — почти всегда про знаменатель, и их
стоит прочитать до того, как доверять любой доле.

## Что в папке и что можно удалить

```bash
./clean.sh          # показать, что лишнее
./clean.sh --yes    # удалить
```

Удаляется только пересоздаваемое: `__pycache__/`, `export/`, `export.zip`,
`captures/`.

**Не трогается** собранное — `data/`, `odds-history.csv`, `changes.csv`,
`mapping.csv`, `pm-resolutions.csv` — и `samples*/`. Последние выглядят как
мусор на 4 МБ, но это записанные кадры, на которых гоняется весь тестовый
набор: без них `npm test` падает.

## Сон ноутбука

`caffeinate -i` не спасает при закрытой крышке: он держит систему от простоя, а
закрытие крышки — отдельный путь усыпления. Помогает только `pmset`:

```bash
sudo pmset -a disablesleep 1     # не спать даже с закрытой крышкой
sudo pmset -a disablesleep 0     # вернуть как было
```

Сборщики теперь переживают потерю сети: `fetch` при пропавшем соединении не
возвращает код, а **бросает** `fetch failed`, и раньше это исключение пролетало
мимо ретраев. Теперь оно ретраится с нарастающей паузой, а сетевой сбой на
старте больше не фатален — цикл обнаружения поднимет сбор сам.

## Экспорт для анализа

```bash
python3 export.py --db data
```

Сутки сбора это пара гигабайт, почти целиком снапшоты стакана. В `export/` и
`export.zip` кладётся то, что нужно для анализа, без этого объёма: отчёт
`analyze.py`, все свипы с контекстом (глубина до обвала, парный токен и границы
справедливой цены, возраст его котировки, максимум цены через 1/5/15 минут,
признак замершей книги), книга вокруг самых глубоких обвалов как временной ряд,
реестр рынков, размеченные филлы целевых кошельков, покрытие по часам, разрывы
и конфиг, с которым шёл сбор. Плюс `README.md`, описывающий колонки и оговорки,
— чтобы файлы читались без этого репозитория.

Порядок величины: десятки-сотни килобайт вместо гигабайтов.

**Заголовок каждого файла объявлен рядом с кодом, который его наполняет**, а
`write_csv` сверяет ключи строки с заголовком в обе стороны и падает с
`SchemaError`. Лишний ключ — такая же ошибка, как недостающий: три бандла
подряд уехали без парных колонок именно потому, что заголовок молча выбрасывал
посчитанное. `README.md` внутри бандла генерируется из фактических заголовков;
колонка без описания печатается со словом `undescribed`.

**`book-series.csv`** — те же величины, что в `sweeps.csv`, но рядом во
времени: один снимок в 30 секунд от пяти минут до обвала до пятнадцати после,
для `--series-sweeps` (300) самых глубоких свипов. Строка `sweeps.csv` не может
показать, как складывается восстановление, а ряд может.

**Свипов в бандл попадает не больше `--max-sweeps` (5000)**, потому что
контекст каждого события стоит отдельного обращения к `book`. Выборка
стратифицирована по дням с равными квотами, внутри дня равномерна по времени, а
`sweeps-strata.csv` говорит, сколько значимых свипов было в каждом дне на самом
деле. Раньше брались просто последние 5000 по времени — на пятидневном прогоне
это оказывался один день, и частота, посчитанная по длине файла, была неверной.
Частоты в любом случае надо брать из `report.txt` и `coverage.csv`, а не из
длины `sweeps.csv`.

`coverage.csv` несёт колонку `gap_seconds` — секунды часа, которых никто не
видел, разложенные по часам из таблицы `gaps`. Без неё разрывы засчитываются в
наблюдённое время и любая частота на рынок-час завышена.

## Разрывы

Каждый разрыв соединения пишется в `gaps` с длительностью и числом
переподписанных активов. Это не диагностика, а часть данных: без этих окон
знаменатель fill rate будет посчитан по времени, которого мы не наблюдали.
