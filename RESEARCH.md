# Исследование лимитных заявок: сбор с 16 сентября 2026

Цель — понять, какие признаки рынка **до исполнения** связаны с выбором рынка,
ценой и объёмом лимитной заявки кошелька. История исполнений показывает только
сработавшие заявки. Публичный стакан не раскрывает владельцев остальных заявок.

## Обновление и запуск

Остановить старый сборщик через Ctrl+C. В терминале в папке проекта:

```bash
git fetch origin
git switch --track origin/codex/research-capture
node --version
npm run pm
```

Если эта ветка уже есть локально: `git switch codex/research-capture`, затем
`git pull --ff-only`. Код проверен на Node.js 24 и Python 3.12. Для Polymarket
достаточно встроенных модулей Node; новые npm/pip зависимости не добавлены.
На Mac вместо последней команды можно выполнить `caffeinate -i npm run pm`.

Если Git сообщает о локальных изменениях, сохранить их коммитом или stash перед
переключением; принудительный checkout не нужен. `data/` остаётся на месте,
новые таблицы добавляются при открытии дневной базы. Полный журнал появится
только после обновления: восстановить пропущенные старым сборщиком события нельзя.

В `pm.config.json` включён `capture.enabled`, контрольный снимок — раз в 60 секунд.
Строка статуса содержит растущий `journal N`. В конфиге три исследуемых адреса:
`0xd403596d8690210994e7f4bae6b9dac1b7e4a817`,
`0xe0f6ee3a23385afdf446c324f9fb69364a272ee6`,
`0x8840126a43353f6cdcd77e90bf2327474a4ef51a`.
Окно подписки начинается за 30 минут до расписания игры. Это расширяет
предматчевой контекст; это не обнаруженный параметр стратегии бота.

## Что собирать и отправлять

Для первой проверки достаточно 6–12 часов активных матчей; затем нужны несколько
дней с реальными исполнениями. Сначала проверить, есть ли контекст **до** новых
филлов нужного кошелька. Количество часов само по себе не гарантирует выборку.

Компактный архив, как раньше:

```bash
python3 export.py --db data
```

Новый непрерывный архив для выбранных UTC-суток:

```bash
python3 research_export.py --db data --since 2026-09-16 --until 2026-09-16
```

Обе даты включены; заменить их на реальные даты сбора. Без `--until` берутся
все дневные файлы начиная с `--since`. Команда напечатает путь
`research-export-<время>.zip`; внутри сжатые JSONL/CSV, README и manifest с
числом строк и фактическим периодом. Передать этот ZIP вместе с `export.zip`.
Чтение не останавливает сборщик, но экспорт активного дня отражает только
снимок базы на момент запуска. Полный журнал занимает больше места; для первой
проверки отправлять один день. Старые SQLite-файлы не удаляются и не сокращаются.

## Что изменилось

- `market_events` сохраняет все распознанные сообщения рыночного WebSocket:
  полный стакан, изменения уровней, `last_trade_price`, смену тика и другие
  события. Сохраняются исходные поля, время приёма, монотонное время процесса,
  идентификаторы сессии/соединения и последовательность. Это распарсенные
  сообщения JSON, не побайтовая запись сетевых кадров; PING/PONG не сохраняются.
- `quote_observations` фиксирует bid/ask обоих исходов **после всего кадра**,
  часы источника, пересечённость книг, bid/ask объём на .01/.011/.02/.03/.05
  и .25/.40/.50/.70/.81/.85/.90, объём и стоимость бидов строго выше уровня.
  Это совокупная видимая ликвидность, а не точная очередь конкретной заявки.
- Раз в минуту и при смене UTC-файла пишется полный контрольный снимок. При
  реконнекте старый стакан сбрасывается; дельты до нового полного снимка не
  считаются достоверным состоянием. Обе стороны рынка могут быть на разных
  соединениях: их часы по-прежнему нужно сравнивать.
- Экспорт и PnL убирают повторы сделок между суточными файлами. Идентичность:
  tx_hash + wallet + asset + side + size + price. Без tx_hash запись не склеивается.
  API без log_index не позволяет разделить одинаковые исполнения внутри одной
  транзакции. Позиции и счётчики разделены по кошелькам.
- `book-series.csv` теперь резервирует 75% окон для падений до 5¢ и ниже,
  остальные — для более высоких цен, с выборкой по дням. Неиспользованные места
  перераспределяются. Раньше ранжирование по удалённому объёму почти вытесняло
  дешёвые свипы. Непрерывный research-export вообще не делает такой выборки.

## Следующий анализ

1. Проверить покрытие: исполнение попало в подписанный интервал, есть полный
   снимок и обновления до него, отсутствуют разрывы. Отдельно учитывать рынки,
   которые начали наблюдать только после первой сделки кошелька.
2. Восстановить уровни **до** исполнения и появления кандидата в заявку.
   Проверять лестницу .90 → .85 → .81 → .70 → .50 → .40 → .25 и дешёвые уровни
   .011/.02; объёмы 200/300/400/500/600/1000 и меняющиеся дешёвые объёмы считать
   гипотезами, а не правилом поиска, исключающим все другие варианты.
3. Сопоставить исчезновение ликвидности с рыночными принтами и подтверждёнными
   филлами кошелька. Без подтверждения это изменение уровня, не доказанный свип
   маркет-ордером и не доказанная отмена лимитки.
4. Сравнить с наблюдавшимися рынками без филла: вид спорта, тип/сегмент рынка,
   время до старта, spread, глубина над ценой заявки, недавние принты,
   волатильность, частота изменений и одинаковые размеры уровней.
   Минутные checkpoint-наблюдения дают контрольные моменты независимо от исхода;
   отсутствие филла не означает отсутствие заявки.
5. Проверять отдельно выбор рынка, цену и размер заявки. Разделять обучение и
   проверку по матчам и датам, сравнивать с простой постоянной лестницей,
   не использовать будущую победу/отскок в признаках принятия решения.

`1 - paired_ask` часто зеркалит bid того же рынка. Он не является независимой
«справедливой вероятностью». У прежних записей добавлялась проблема расчёта
парной метрики между двумя изменениями одного кадра. Старые значения не
пересчитываются без исходного потока; новые позволяют проверить это явно.

## Проверки разработки

```bash
npm run test:pm
```

Запускает все тесты модулей Polymarket и четыре Python-набора, включая реальную
SQLite → экспорт → чтение архива цепочку. Live-соединение с Polymarket и
многосуточная нагрузка должны проверяться на машине сбора.
