## Актуальное дополнение: 2026-09-17 — подписанные заявки

Это дополнение приоритетнее старых чисел и конфигураций ниже.
`order_decode.py` декодирует прямой V2 matchOrders и сопоставляет **все** заявки
с OrderFilled из receipt; не выбирает один ордер по приблизительной цене API.
`order_research.py` — отдельный read-only процесс (`npm run pm:orders`), SQLite
`data/order-research.sqlite`, кеш исходных RPC и явный журнал ошибок. Поддержаны
два V2 exchange, обе роли, direct/mint/merge; неизвестные форматы не угадываются.
Стандартная библиотека Python, без новых зависимостей и торговых вызовов.

`order_context.py` связывает уникальные подписанные заявки с анонимной книгой
до client timestamp. Контекст -60/-10/-1/0 секунд, без будущих образцов; статус
пропусков/reset/устаревания/пересечения и часы источника сохраняются.
`research_export.py` дополнительно экспортирует signed-orders, chain-fills,
counterparty-fills, creation-context, raw RPC и ошибки. Без order DB выдаёт
предупреждение; прежний сборщик/компактный экспорт работают независимо.

Ключевые ограничения: signed timestamp != posting/acknowledgement; возраст до
блока != период перестановки; первая наблюдаемая заливка != первая за всю жизнь.
Частичные филлы одной заявки объединяются по exchange+order_hash; события — по
chain+tx+log_index. Тейкерский original_shares — размер при лимитной цене;
улучшение цены может дать больше долей при том же денежном бюджете.
История только исполненных заявок не идентифицирует отмены и владельцев L2.

Четыре адреса из текущего задания, включая 0xdaffa…; ITF/MLB явно добавлены в
подписываемые дисциплины. Перечни labels/disciplines не объединяются. Потолок
150 на спорт оставлен и добавлен в DEFAULTS; ITF делит теннисный бюджет.
Старое решение держать эти два префикса только в labels заменено текущим планом.

Проверки: npm run test:pm, включая реальные tx/receipt fixtures и цепочку
Store/Capture → создание контекста → экспорт. Запуск и ограничения: RESEARCH.md.

`BookFeed.onBatch` передаёт целый кадр; все изменения обоих исходов применяются

ложную рассинхронизацию. После reset дельты не создают стакан без полного book.

`research_export.py` экспортирует непрерывный журнал и таблицы в сжатый архив
без отбора по свипам/будущим филлам. Поддерживает включительные UTC-даты
`--since` / `--until`. Форматы и восстановление состояния описаны в README
самого архива. `capture_start` содержит фактически применённый конфиг; при
экспорте последующих суток старт сессии может находиться в более раннем файле.

`trade_identity.py` убирает одинаковые API-филлы между днями. `export.py` и
`analyze_fills.py` используют эту функцию, позиции разделены по wallet+asset,
PnL в архиве строится из свежего очищенного CSV. `fill_index` в target-fills
пересчитывается по wallet+asset+side; это номер в выбранной истории, не lifetime.
`Store.fillOrdinal` и квоты дисциплин также убирают суточные повторы. Контекстный
ordinal видит только текущую и предыдущую базу, считает все сделки до timestamp
включительно; сделки в одну секунду могут иметь одинаковый счётчик. Старый
fill-context автоматически не исправляется. Сводные rate-отчёты `analyze.py`
сохраняют прежнюю методику; новые гипотезы проверять на очищенных филлах и журнале.

В pm.config.json: leadMinutes=30; capture включён; три адреса (0xd403…, 0xe0f6…,
0x8840…). Решение от 5 сентября убрать 0x8840… заменено текущим списком
исследования. Поллинг кошельков не запускает новый цикл поверх незаконченного.
Список дисциплин не расширялся: вне него есть только follow после активности
кошелька. Для таких рынков предшествующего контекста может не быть.

`book-series.csv` резервирует 75% окон для bid_after<=.05, с выборкой по дням
и перераспределением свободных мест. Это подвыборка sweeps.csv, не контрольная
выборка всех рынков. `fair_lower_bound=1-paired_ask` не независимая оценка
вероятности: книги могут зеркалить одну ликвидность. Одинаковые размеры на
уровне — анонимный кандидат, а не идентифицированная заявка кошелька.

Проверки: `npm run test:pm`. Нужны Node.js 24 (проверено) и Python 3; новых

## 1. Что это за проект

Изучается кошелёк на Polymarket, который ставит пассивные лимитные биды по
1–2 цента на живых суб-рынках киберспорта и тенниса (Map/Game/Set Winner,
гандикапы, тоталы) и часто закрывается в течение 1–4 минут. Рабочая гипотеза:
это не прогноз исхода, а ловля «аварий книги» — крупная рыночная продажа
съедает стакан до дна, хотя честная вероятность события остаётся 15–40%.
Проверить гипотезу по публичной истории сделок нельзя: неисполненные заявки
нигде не сохраняются, поэтому единственный способ получить знаменатель —
самому непрерывно писать стакан и параллельно фиксировать независимую оценку
честной вероятности.

Отсюда две половины. Первая — сборщик gg.bet: Playwright открывает живые
страницы по CS2, Dota 2, LoL, Valorant и теннису, слушает два GraphQL-вебсокета
и пишет котировки букмекера и полный журнал изменений в матчах. Вторая —
сборщик Polymarket: раз в 45 секунд находит живые суб-рынки через Gamma API,
держит их стаканы на CLOB-вебсокете, пишет каждое обновление и каждый удар по
книге, тянет сделки целевых кошельков и сшивает всё это с котировками gg.bet,
получая отношение «честная вероятность / цена Polymarket» в момент события.

Поверх собранного лежат четыре Python-скрипта: `analyze.py` (частота свипов,
fill rate, payoff, ёмкость), `analyze_fills.py` (PnL целевых кошельков по
позициям и режимам выхода), `export.py` (бандл на ~535 КБ для отправки в
аналитический чат), `check.py` (проверка полноты сбора). Всё read-only по
отношению к Polymarket: ни ключей, ни подписи ордеров, ни выставления заявок —
это жёсткое требование заказчика и оно не обсуждается.

## 3. Как это запускается

### Что должно быть установлено

- **Node 22 или новее.** Хранилище использует `node:sqlite`, а он появился в
  Node 22. `engines` в `package.json` теперь говорит `>=22` (раньше стояло
  `>=20`, и это было неверно: на Node 20 `collector.mjs` падал на импорте).
- **Python 3.10 или новее** (только стандартная библиотека: `sqlite3`, `csv`,
  `statistics`, `zipfile`). Ни venv, ни pandas не нужны. Разбор времени идёт
  через `analyze.py::parse_timestamp`, а не через `datetime.fromisoformat`
  напрямую — почему, см. §8.
- **Playwright + Chromium** — только для gg.bet-половины:
  `npm install && npx playwright install chromium`.
- Никаких ключей, токенов и переменных окружения проект не требует.

### Переменные окружения

- `NODE_USE_ENV_PROXY=1` — нужна **только** если Node ходит через прокси-агент
  (в песочнице Claude Code). Встроенный `fetch` в Node иначе игнорирует
  `HTTPS_PROXY`. На обычном ноутбуке не нужна.
- `--proxy http://user:pass@host:port` — флаг `monitor.mjs`, не переменная.

### Порядок старта

Два процесса, **строго раздельно**, в двух терминалах:

```bash
npm run watch     # gg.bet: пишет odds-history.csv и changes.csv
npm run pm        # Polymarket: пишет data/pm-<дата>.sqlite
```

Порядок в целом не важен, но `collector.mjs` читает `odds-history.csv` хвостом:
пока gg.bet-сборщик не написал ни строки, таблица `joined` будет пустой, а всё
остальное соберётся. Разносить процессы обязательно: Playwright периодически
падает и перезапускается, а дырка в стакане — это дырка в знаменателе fill rate.

Аналитический конвейер, строго в этом порядке:

```bash
python3 export.py --db data                       # 1. пишет export/target-fills.csv
node src/pm/resolve.mjs --from export/target-fills.csv   # 2. pm-resolutions.csv
python3 analyze_fills.py --fills export/target-fills.csv # 3. PnL
python3 export.py --db data                       # 4. кладёт PnL внутрь бандла
python3 check.py                                  # 5. проверка
```

Второй прогон `export.py` не лишний: он сам вызывает `analyze_fills.py` и
кладёт `fills-report.txt` в архив, а на первом прогоне резолюций ещё нет.

### Как понять, что процесс жив, а не завис

- `collector.mjs` раз в 60 секунд печатает в stderr строку `[status] N books |
  M rows | ... | data/pm-<дата>.sqlite`. Если `rows` не растёт между двумя
  строками — стакан не идёт.
- При старте и при каждом изменении набора пишется `[discovery] N markets,
  M tokens (+a -b)`. Если этого нет — Gamma не отвечает.
- `[feed] socket close, reconnecting in Ns` — нормальный реконнект; каждый
  такой разрыв попадает в таблицу `gaps` и вычитается из покрытия.
- `monitor.mjs` перерисовывает таблицу раз в `--interval` (5 с по умолчанию).
  Строка `missing: Теннис 12/28 — list not fully loaded` означает, что список
  матчей недокручен, не что матчей нет.
- Внешняя проверка в любой момент: `python3 check.py`.

## 4. Схема данных

### SQLite, `data/pm-<YYYY-MM-DD>.sqlite`

Один файл на UTC-сутки. `PRAGMA journal_mode = WAL`, `synchronous = NORMAL`.
Запись буферизуется и уходит транзакцией раз в 1000 мс или каждые 2000 строк.

**`markets`** — реестр отслеживаемых рынков, PRIMARY KEY `condition_id`.
`condition_id, asset_id_a, asset_id_b, question, slug, event_slug, event_title,
sport, level, kind, segment_kind, segment_no, line, team_a, team_b, outcome_a,
outcome_b, end_date, tick_size, min_size, first_seen, last_seen,
game_start_time, subscribed_at, unsubscribed_at, release_reason,
observed_during_game`.
`level` — `segment` или `match`; `kind` — `winner`/`handicap`/`total`;
`segment_kind` — `map`/`game`/`set`, NULL для матчевых рынков; `line` NULL для
winner. **Дозаполняется:** при повторной встрече рынка обновляются только
`last_seen`, `end_date`, `tick_size`, `min_size` — остальное пишется один раз.
`team_a/team_b` могут быть NULL, если названия не вытащились из вопроса.
`game_start_time` — время начала матча из Gamma (`gameStartTime`), на нём стоит
всё окно подписки. `observed_during_game` — 0/1, взводится живьём при первой
книге внутри интервала игры и **никогда не сбрасывается** обратно (в upsert
стоит `max(старое, новое)`, потому что суточная ротация переписывает все
отслеживаемые рынки в новый файл). Это самопроверка сбора, видимая без анализа:
доля единиц среди сыгранных матчей и есть критерий «смотрели ли мы игру».
`release_reason` — `resolved`, `past the hold window` или
`window passed unwatched`.

**`book`** — сердце сбора, ~25 млн строк за пять дней.
`ts, asset_id, condition_id, trigger, best_bid, best_ask, mid, size_at_001,
size_at_002, size_at_003, size_at_005, depth_bid_total, depth_ask_total,
n_bid_levels, spread, paired_bid, paired_ask, fair_mid, book_sum,
paired_stale_seconds`.
Последние пять — второй исход того же рынка. Оба токена подписаны всегда, обе
книги лежат в одной карте в памяти, поэтому это стоит одного обращения к Map.
`fair_lower_bound` здесь **не хранится**: это `1 - paired_ask`, а таблица идёт
на десятки миллионов строк. `book_sum` — сумма лучших бидов обеих сторон; в
работающем рынке она чуть меньше единицы, сильно ниже — это отсутствующая
сторона книги, а не другая оценка вероятности.
`trigger` — `book` (полный снапшот), `change` (инкремент), `heartbeat`
(по таймеру раз в 5 с независимо от движения). **Только `heartbeat` доказывает,
что мы смотрели** — покрытие считается по ним.
`best_bid`/`best_ask` NULL, когда соответствующая сторона пуста; `mid` и
`spread` NULL, если пуста хоть одна.

**`sweeps`** — сработки детектора.
`ts, asset_id, condition_id, rule, bid_before, bid_after, size_consumed,
levels_crossed, depth_before, depth_after, levels_touched, size_eaten_partial,
n_bid_levels_before, sweep_id, ggbet_fair, dislocation_ratio,
seconds_since_ggbet_quote, ggbet_market_state, paired_asset_id, paired_bid,
paired_ask, paired_ask_size, fair_lower_bound, fair_upper_bound, fair_mid,
book_sum, internal_dislocation, paired_stale_seconds`.
`fair_lower_bound = 1 - paired_ask` — нижняя граница справедливой цены, взятая
из стоящих заявок, а не из внешнего фида: у бинарного рынка два токена платят
доллар на двоих, значит предложение продать второй по 0.85 кладёт под первый
пол в 0.15. `internal_dislocation = fair_lower_bound / bid_after` — во сколько
раз бид ушёл ниже этого пола. `paired_ask_size` обязательна к учёту: одинокая
доля по 0.99 даёт пол 0.01 и не значит ничего. `paired_stale_seconds` — возраст
последнего **реального** изменения книги близнеца, хартбит его не двигает.
`sweep_id` = `<asset_id>:<ts>` — своего ключа у таблицы нет, а запись
буферизована, поэтому rowid в момент события неизвестен. Четыре последние
колонки пишутся **в момент события** из резидентного кеша котировок gg.bet:
лукап постфактум по таблице `joined` находил котировку для 1 свипа из 5000,
потому что строка `joined` пишется только при движении книги и с моментом
свипа почти никогда не совпадает.
`rule` — одно или несколько из `bid_drop`, `levels`, `depth_collapse`,
склеенных через `+`. `bid_after` NULL, когда книга опустела целиком.
Пишется **либерально**, фильтр значимости применяется в анализе (§6).

**`sweep_followups`** — что стало с бидом после свипа.
`sweep_id, asset_id, condition_id, horizon, high_bid, filled_at,
resolved_before_horizon, book_frozen`, `UNIQUE (sweep_id, horizon)`.
`book_frozen = 1` — за весь горизонт по активу не пришло ни одного реального
обновления книги: рынок умер в момент обвала (определился тотал, закрылся
гандикап), а не «свип, в который никто не вернулся». `NULL`, если часы книги
не передали: нет базы для сравнения — нет утверждения.
`horizon` — 1, 5 или 15 минут. `high_bid` — максимум лучшего бида за окно,
считается бегущим максимумом по уже приходящим снапшотам: ни запроса к API, ни
обращения к базе. `resolved_before_horizon = 1` означает, что рынок
резолвился раньше срока и `high_bid` — это выплата, а не бид; без флага
отличить расчёт от «никто не бидовал» невозможно. Отписка от рынка посреди
горизонта тоже пишет строку — с тем, что успели увидеть, а не дырку.

**`joined`** — Polymarket против gg.bet.
`ts, condition_id, asset_id, pm_best_bid, pm_best_ask, pm_mid, ggbet_fair,
ggbet_market_state, score, segment_score, dislocation_ratio,
seconds_since_ggbet_quote`.
`ggbet_fair` — вероятность после devig, уже развёрнутая на нужную сторону
токена. `dislocation_ratio = ggbet_fair / pm_mid`, NULL если нет одной из
частей. `seconds_since_ggbet_quote` — возраст котировки букмекера; gg.bet пишет
строку только при изменении цены, поэтому без этого поля нельзя отличить
реальное расхождение от замершей котировки.

**`wallets`** — сырая активность целевых адресов, `UNIQUE (address, activity_id)`.
`ts, address, activity_id, type, side, asset_id, condition_id, price, size, tx_hash`.
`activity_id` собран из полей записи, потому что своего id у неё нет.

**`trades`** — сделки **только целевых кошельков**, с ролью.
`ts, condition_id, asset_id, wallet, side, price, size, role, tx_hash`,
`UNIQUE (tx_hash, wallet, asset_id, side, size, price)`.
`role` — `maker` или `taker`, вычисляется в момент выкачки (см. §7), позже не
меняется.

**`trade_scans`** — по одной строке на скан рынка, чтобы рыночный фон не
потерялся вместе с выброшенными чужими сделками.
`ts, condition_id, total_trades, wallet_trades, taker_share, pages, truncated`.
`truncated = 1` означает, что журнал не дочитан и любая доля, посчитанная из
него, занижена.

**`universe`** — журнал всего, что видел discovery, PRIMARY KEY `condition_id`.
`ts, condition_id, discovered_via, subscribed, unsubscribed_at, reason_skipped,
question, sport, level, kind`.
`subscribed` — 0/1. `reason_skipped` — пустая строка для подписанных, иначе
текст вида `unmapped discipline: mlb`, `order book disabled`,
`expected 2 tokens, got N`. **`unsubscribed_at` дозаполняется позже** — когда
рынок уходит из выдачи discovery (единственный `ON CONFLICT DO UPDATE` в схеме).

**`fill_context`** — книга вокруг филла целевого кошелька. Ради неё всё и
собирается.
`fill_ts, asset_id, condition_id, wallet, side, price, size, fill_index,
bid_t_minus_60, bid_t_minus_10, bid_t_minus_1, ask_t_minus_1,
size_at_002_before, depth_before, paired_bid_before, fair_lower_bound_before,
book_sum_before, bid_plus_60, bid_plus_300, bid_plus_900, matched_sweep_id,
snapshot_available, filled_at`.
Заполняется отложенным воркером через 15 минут после филла, из уже записанных
снимков: филл становится известен из опроса журнала сделок через десятки
секунд, а следующие 15 минут ещё не наступили. **`snapshot_available` читать
первой**: 0 означает, что рынок не наблюдался и пустые колонки не говорят
ничего; 1 с пустыми колонками означает, что книга действительно была пуста.
Выборка образца ограничена по свежести: строка старше искомого момента на
полминуты образцом не считается, иначе снимок шестичасовой давности читался бы
как живая котировка. **Ограничение действует только на `bid_t_minus_*`.**
Колонки `*_before` берут ближайшую предшествующую строку без окна вообще
(`Store.bookAt`), поэтому пустое `fair_lower_bound_before` означает буквально:
до филла по этому активу в базе нет ни одной строки книги.

**В очередь попадают не все филлы.** Если рынок был уже закрыт в момент, когда
`followWallets` до него добрался, строка контекста не пишется вовсе: книги
вокруг такого филла нет и быть не могло — никто не наблюдал и не мог. Иначе
получается строка из нулей с `snapshot_available = 0`, честная и бесполезная:
1873 таких из 1883 хоронили те 10, на которые ответ был, и вся подписка
читалась как ловящая полпроцента филлов, хотя ловила всё, до чего могла
дотянуться. Сами филлы остаются в `trades` и в `target-fills.csv`; счётчик
пропущенных виден в статусной строке коллектора, а `check.py` печатает оба
знаменателя.

Отсюда же следствие, которое надо держать в голове: **для рынка, о котором мы
узнали из самого филла, колонки `*_before` не заполнятся никогда** — прошлого у
нас нет. Поднять их долю можно только более широкой и ровной подпиской
(`schedule.maxLivePerSport`), а не более длинным поиском назад.

**`gaps`** — окна, которых никто не видел.
`started_at, ended_at, duration_ms, reason, assets_resubscribed`.
`reason` сейчас всегда `reconnect`.

Индексы: `book_asset_ts`, `sweeps_asset_ts`, `joined_cond_ts`, `trades_asset_ts`,
плюс `book_trigger_asset_ts` и `book_bid_asset_ts` — последние два добавлены
потому, что без них запросы покрытия и fill rate уходят в полный скан и минуты
на вопрос. `analyze.py` умеет достроить их сам (`ensure_indexes`).

### CSV gg.bet

**`odds-history.csv`** — одна строка на изменение цены:
`ts, sport, match_id, title, score, segment, segment_score, market, selection,
price, is_active`. `title` может быть uuid, если патч пришёл раньше снапшота
с названиями команд.

**`changes.csv`** — упорядоченный журнал всего, что происходило:
`seq, ts, sport, match_id, title, kind, target, from, to`.
`kind` ∈ `match_start`, `score`, `segment`, `segment_name`, `segment_score`,
`round`, `state`, `bet_stop`, `price`, `market_open`, `market_closed`,
`odd_suspended`, `odd_resumed`. `target` NULL для скалярных полей матча и
заполнен строкой `<рынок> / <исход>` для событий по котировкам.

**`mapping.csv`** — соответствие рынков:
`pm_condition_id, ggbet_match_id, pm_segment, ggbet_segment, confidence,
verified, pm_level, pm_kind`.
Последние две добавлены, чтобы вопрос «какая доля таблицы — победители
сегментов» отвечался по самому файлу: кошельки торгуют именно их.
`confidence` ставит матчер, `verified` ставится **только руками**; строка с
`verified=1` больше никогда не переписывается автоматически.

### Файлы резолюции

**`pm-resolutions.csv`** — по строке на исход (две на рынок):
`condition_id, token_id, outcome, winner, payout_price, closed, question,
market_slug, end_date_iso, game_start_time, min_tick_size, min_order_size,
sport, market_level, kind, segment_no, fetched_at`.
`winner` — `1`, `0` или пусто (рынок ещё не закрыт). Последние пять колонок
выходят за согласованную схему: классификация делается здесь, чтобы правила
жили в одном месте, а не в двух языках. Файл **сам себе кэш**: закрытый рынок
второй раз не запрашивается.

**`pm-position-gaps.csv`** — позиции с неполной историей:
`asset_id, condition_id, buy_size, sell_size, first_side, reason`.
`reason` ∈ `no buys recorded`, `first trade is a sell`, `sells exceed buys`.

### Бандл `export.zip` (14 файлов, ~600 КБ)

`README.md`, `report.txt` (вывод `analyze.py`), `fills-report.txt` (вывод
`analyze_fills.py`), `sweeps.csv` (46 колонок, с контекстом на момент события),
`book-series.csv` (книга вокруг самых глубоких свипов как временной ряд, один
снимок в 30 секунд от −5 до +15 минут),
`sweeps-strata.csv` (сколько значимых свипов было в каждом дне и сколько попало
в выборку),
`markets.csv`, `target-fills.csv`, `fill-context.csv`, `coverage.csv`,
`universe-summary.csv`,
`gaps.csv`, `pm-resolutions.csv`, `pm-position-gaps.csv`, `mapping.csv`,
`pm.config.json`. Плюс `target-fills-prior.csv`, если в корне лежит более
ранний экспорт.

**Список колонок каждого файла объявлен рядом с кодом, который его наполняет**
(`SWEEP_COLUMNS`, `BOOK_SERIES_COLUMNS` в `export.py`, `FILL_CONTEXT_COLUMNS` в
`fill-context.mjs`), а `write_csv` сверяет ключи строки с заголовком **в обе
стороны** и падает с `SchemaError`. Лишний ключ — такая же ошибка, как
недостающий: три бандла подряд уехали без парных колонок именно потому, что
заголовок молча выбрасывал то, что коллектор посчитал и сохранил. `README.md`
внутри бандла тоже генерируется из фактических заголовков, а не из шаблона;
колонка без описания печатается со словом `undescribed`, а `npm test` на такую
падает.

## 5. Конфигурация (`pm.config.json`)

Файл перекрывает `DEFAULTS` из `src/pm/config.mjs` поверхностным merge по
верхним ключам: достаточно указать только меняемую секцию. Если файла нет,
работают дефолты. Сборщик gg.bet этот конфиг **не читает** — у него свои флаги.

### `disciplines` — что подписывается

Префикс event-slug → `sportId` gg.bet. Сейчас 12 записей: `cs2`, `csgo`,
`dota2`, `dota`, `lol`, `val`, `valorant`, `r6`, `atp`, `wta`, `tennis`,
`codmw`.
`itf`, `setka`, `setkameua` **перенесены в `labels`**: после перехода на
подписку по игровому окну они подписывались бы целиком, а Polymarket создаёт их
пачками по тысяче штук и играют они круглосуточно — это примерно восьмикратный
рост таблицы `book`. Их по-прежнему можно назвать, но за ними не следят.
Дисциплина берётся **из префикса слага события**, а не из вопроса: вопрос
«Map 1 Rounds Handicap: A (-6.5) vs B (+6.5)» не называет спорт вообще.
Добавление префикса сюда **расширяет подписку** и увеличивает нагрузку.

### `labels` — что можно только назвать

`itf→tennis, setka/setkameua→table_tennis, mlb→baseball, nba→basketball,
nfl→american_football, nhl→ice_hockey, epl→football, ucl→football,
pol→politics, us→politics, fin1→finance, bitcoin→crypto,
eth/ethereum/xrp/sol/doge→crypto`.
Используется **только** резолвером, чтобы у сделки кошелька в чужой дисциплине
была подпись. **Не путать с `disciplines`** — перенос записи оттуда сюда молча
расширит подписку в разы (в реальном прогоне под `mlb` прошло 2232 рынка).

### `gamma`

- `intervalSeconds: 45` — период discovery. Меньше 30 — лишняя нагрузка без
  выигрыша: суб-рынки создаются за минуты до матча. Больше 90 — начинают
  теряться короткие карты.
- `pageSize: 100` — **потолок Gamma**. Больше просить бесполезно, вернётся 100.
- `maxPages: 12` — то есть до 1200 рынков за круг при сортировке по
  `startDate desc`. Уменьшение обрезает хвост живых рынков. **Это глубина
  обнаружения, а не окно подписки**: раньше она была и тем и другим, и отсюда
  брался весь баг с окном (§6).
- Обход останавливается досрочно, если страница не принесла ни одной новой
  записи. Сортировка идёт по неуникальному ключу — тысяча рынков может иметь
  один и тот же `startDate` до секунды, — и offset-пагинация по такому ключу
  повторяет уже выданные строки: 20 страниц по 100 дали 1119 уникальных
  рынков, причём шесть страниц не добавили ничего.

### `schedule` — окно подписки

- `leadMinutes: 10` — за сколько до начала матча подписываться.
- `tickSeconds: 10` — как часто двигать окно. Намеренно чаще, чем discovery:
  десятиминутный запас не имеет смысла, если его проверяют раз в 45 секунд.
- `holdHours` — сколько после начала матч ещё может идти, по `sportId` gg.bet.
  CS2/LoL/Valorant/R6/CoD — 6, Dota 2 — 8, теннис — 5, настольный теннис — 2,
  `default: 6`. Это верхняя граница удержания, а не ожидаемая длительность.
- `maxAheadHours: 72` — рынки, датированные только через дедлайн резолюции,
  дальше этого не планируются.
- `resolutionCheckMinutes: 15`, `resolutionCheckAfterMinutes: 45`,
  `resolutionsPerCycle: 20` — опрос CLOB на предмет `closed=true`. Настоящая
  причина отписки — резолюция; `holdHours` только страховка. Спрашивать
  начинают лишь когда матч мог закончиться, и не чаще, чем указано.

### `followups` и `fillContext`

- `followups.horizons: [1, 5, 15]` — минуты, на которых фиксируется максимум
  бида после свипа. Меняются свободно: считается из уже собранных снапшотов.
- `fillContext.settleSeconds: 900` — сколько ждать после филла, прежде чем
  писать его контекст. Должно быть не меньше самого дальнего окна `bid_plus_*`.
- `fillContext.maxAgeHours: 24` — насколько вглубь истории кошелька имеет смысл
  писать контекст. Журнал сделок отдаёт историю, а не новости: первый же опрос
  возвращает сотни филлов за прошлые дни, и без этого ограничения таблица
  заполняется строками «книга не наблюдалась», что верно (сборщика тогда не
  было) и бесполезно, а нужные филлы в них тонут.

### `wallets.followHours`

`48` — насколько свежим должен быть филл, чтобы рынок взяли под наблюдение по
приоритету кошелька. Активность отдаётся тысячами записей вглубь, и без
ограничения в подписку уезжали долгоиграющие рынки вроде «Will Bitcoin reach
$1,000,000 by December 31», каждый — до самой резолюции.

### `schedule.maxLiveMarkets`

`null`, то есть потолка нет и ничего не нормируется. Когда он задан, свободные
слоты раздаются по тому, **где кошельки реально торговали за последнюю неделю**
(доли считаются из таблицы `trades`), а не по тому, сколько рынков дисциплины
оказалось в выдаче API. Рынок, в котором кошелёк уже засветился, слота не ждёт
никогда.

### `schedule.maxLivePerSport`

`150` — жёсткий потолок числа одновременно наблюдаемых рынков **на дисциплину**.
Ранжирование (`#rank`) решает, кто пойдёт первым, когда слотов не хватает; оно
не ограничивает *состав*. Polymarket создаёт теннисные под-рынки с частотой, до
которой остальным дисциплинам далеко, и при запасе слотов теннис забирает всё:
один сбор вышел на 73% теннисным, предыдущий — на 60% CS2, и вывод, снятый с
одного, ничего не говорит о другом. Потолок делает доли сравнимыми между
прогонами.

Рынки кошелька (`source: 'wallet'`) от потолка освобождены, но **в счёт идут**:
это тоже наблюдаемые рынки этой дисциплины. Если кошелёк работает в теннисе
плотно, он выберет теннисный бюджет — и это правильно, ради его рынков всё и
собирается.

Ожидаемый эффект по прошлым числам: теннис 842 → 150, CS2 582 → 150, LoL и
Valorant почти не задеты, Dota не задета. Доля крупнейшей дисциплины уходит
примерно к 30%, объём базы падает примерно втрое. Проверять по `check.py`,
строка «the largest discipline is N% of M deep sweeps».

### `book`

- `heartbeatSeconds: 5` — как часто пишется строка `heartbeat` по каждому
  токену. **Это единица покрытия**: `analyze.py` считает рыночные часы из
  количества heartbeat-строк (`HEARTBEAT_SECONDS = 5` захардкожен в анализаторе).
  Изменение здесь без правки анализатора исказит все частоты.
- `reconnectMinMs: 1000`, `reconnectMaxMs: 60000` — экспоненциальный backoff.

### `sweep` — детектор ударов по книге

- `levelsCrossed: 3` — сколько уровней должно быть съедено для правила `levels`.
- `bidDropTicks: 3` и `bidDropMin: 0.02` — порог падения лучшего бида: берётся
  **максимум** из трёх тиков этого рынка и 0.02 абсолютных. Тик у Polymarket
  разный: из выборки киберспортивных рынков 58 идут с шагом 0.01 и 7 с 0.001;
  на 0.001 три тика — это 0.003, что срабатывало бы на шуме.
- `depthWindowSeconds: 10`, `depthDropRatio: 0.5`, `depthAbovePrice: 0.05` —
  правило обвала глубины: суммарный объём бидов выше 5 центов потерял больше
  половины за 10 секунд.
- `minBidBefore: 0.05` — книге, которая уже стояла на центе, обваливаться
  некуда. **Без этого порога считались все блики пустой книги.**
- `minSizeConsumed: 100` — минимум съеденного объёма.
- `minDepth: 100` — минимальная глубина до события.
- `cooldownSeconds: 30` — один обвал приходит пачкой апдейтов; без кулдауна
  одно событие записывалось на каждом из них.
  Эти четыре параметра добавлены после первого дня, который дал 617 281
  «свипов». Их снятие вернёт мусор.

### `wallets`

- `intervalSeconds: 25` — период опроса активности.
- `addresses` — **один** адрес под изучением:
  `0xd403596d8690210994e7f4bae6b9dac1b7e4a817`.
  Отсюда же его читает `analyze.py` и `export.py` — список в одном месте.

  Второй адрес, `0x8840126a43353f6cdcd77e90bf2327474a4ef51a`, убран 5 сентября
  по решению владельца проекта. За сбор 02–04 сентября он не дал **ни одной**
  сделки: все 1883 филла принадлежат первому адресу. При этом он стоил запроса
  активности каждые 25 секунд, а его история — появись она — размыла бы
  `walletDisciplineShares`, потому что квоты подписки считаются по таблице
  `trades` для всех адресов сразу, без разделения. Если понадобится следить за
  вторым адресом — вернуть строку в массив, больше нигде ничего менять не надо.

### `trades`

- `intervalSeconds: 120` — не чаще одного раза в две минуты на один рынок.
- `marketsPerCycle: 25` — потолок рынков за круг. Роль стоит **двух** полных
  постраничных обходов на рынок, поэтому опрашиваются только те рынки, где
  целевой кошелёк действительно торговал.

### `ggbet`

- `oddsHistory: odds-history.csv`, `changes: changes.csv`, `mapping: mapping.csv`
  — пути к файлам чужого сборщика, читаются хвостом, **не переписываются**.
- `matchWindowHours: 6` — окно, в котором матч gg.bet считается кандидатом на
  сшивку с рынком Polymarket.
- `pollSeconds: 5` — как часто дочитывается хвост `odds-history.csv`.

### `storage.dir: data`

Каталог дневных баз.

## 6. Решения и их причины

Это раздел «не чинить». Каждый пункт выглядит странно и имеет причину.

**Хранилище — `node:sqlite`, один файл на UTC-сутки.** Встроен в Node 22:
ни драйвера, ни сборки, ноль npm-зависимостей у сборщика (единственная
зависимость проекта — Playwright, и та только для gg.bet). Сутки — это
примерно гигабайт при 500 токенах; файл на день держит размер рабочим и даёт
анализатору открывать только нужный диапазон дат. Запись буферизована:
при ~100 строках в секунду транзакция на строку уйдёт целиком в fsync.

**Два независимых процесса, а не один.** Playwright падает и перезапускается;
разрыв в стакане Polymarket — это дыра в знаменателе. Общая судьба у них
недопустима.

**`disciplines` и `labels` разделены.** Первое решает, за чем следить, второе —
что уметь назвать. Слияние молча расширило бы вселенную подписки.

**Свипы пишутся либерально, значимость применяется в анализе.** Обвал, не
дошедший до цента, — это знаменатель fill rate, он нужен в сыром логе. Порог
(`--min-bid-before`, `--min-consumed` в `analyze.py`) можно перекрутить без
пересбора. Отсюда же расхождение: 648 364 записи в базе против 117 616
значимых в отчёте — это не ошибка.

**Окно подписки определяется временем матча, а не выдачей Gamma.** Это самое
дорогое исправление в проекте, и оно объясняет, почему первые пять дней сбора
не пересекались со сделками кошельков ни одной строкой. Раньше реестр был
зеркалом текущей страницы Gamma: рынок подписывался, как только попадал в
первые 1200 по `startDate desc`, и отписывался, как только его оттуда
вытесняли более новые. Время жизни в этом окне — это `1200 / скорость создания
рынков`, то есть примерно час (замер по живому API: страница глубиной 1200
покрывала 34 минуты), и к матчу оно отношения не имеет. Рынки создаются за
11–15 часов до игры, значит наблюдался час сразу после создания, а матч играли
через сутки, когда никто не смотрел. Медиана наблюдения 61 минута и ноль
пересечений с филлами — это оно.

Теперь discovery только **добавляет** в расписание, а подписку и отписку решают
часы: `game_start − leadMinutes` на вход, резолюция или `game_start + hold` на
выход. Выпадение из выдачи Gamma больше не событие. Сортировка `startDate desc`
осталась как была — она отвечает за обнаружение.

**Расписание переживает рестарт.** Оно живёт в памяти, а рынок виден
discovery всего около часа после создания — за 11–15 часов до игры. Значит
перезапуск в промежутке уронил бы все матчи, запланированные на остаток суток,
и Gamma их больше не показывает: потеря была бы полной и молчаливой. При старте
`restoreSchedulableMarkets()` читает последние дневные базы и возвращает в
расписание рынки с непрошедшей игрой и пустым `unsubscribed_at`. На живой
проверке: круг discovery дал 5 рынков, из прошлого прогона восстановилось 20.

**`end_date` не участвует в окне.** Это дедлайн резолюции, а не конец игры:
замер по живому API даёт `game + 6ч` для CS2 и `game + 168ч` (ровно неделя) для
ITF. Отписка по нему держала бы теннисный стакан семь суток после матча, а
критерий «`last_seen >= end_date_iso`» невыполним по построению. Проверять надо
`observed_during_game`.

**Сортировка Gamma по `startDate desc`.** Живые суб-рынки создаются
непосредственно перед матчем. Сортировка по id или объёму хоронит их под
долгоиграющими политическими и крипто-рынками.

**Подписка чанками по 250 активов на сокет.** Набор задаётся в момент
подключения, поэтому изменение списка переподключает **только свой чанк**.
Discovery сообщает лишь реальные добавления и удаления, так что это случается
на старте и конце матча, а не каждый круг.

**Из журнала сделок хранятся только сделки целевых кошельков.** Первый заход
записал 214 тысяч строк и 180 МБ ради установления роли у горстки филлов.
Рыночный фон сохраняется одной строкой `trade_scans` на скан.

**Роль восстанавливается разностью множеств.** В записях сделки нет флага
роли. `takerOnly=true` возвращает строгое подмножество `takerOnly=false`;
разность — пассивные исполнения. Проверено вживую на условии `0x3c9b7d57`:
124 тейкерских записи внутри 367, целевой кошелёк только среди 243 мейкерских.

**Выборка свипов стратифицирована по дням.** Раньше бралось `sweeps[-5000:]`
после сортировки по времени — то есть последние 5000 в файле, описанном как
«последние 5000 из 117616». На пятидневном прогоне это был один день, и любая
частота, посчитанная по длине файла, была неверной. Теперь квоты по дням
равные, внутри дня выборка равномерная по времени, а `sweeps-strata.csv`
говорит, сколько значимых свипов было в каждом дне на самом деле.

**Псевдонимы команд вместо одной пары имён.** Polymarket пишет в `outcomes`
победителя сегмента фамилии («Yamaguchi», «Back»), а в `eventTitle` — полные
имена, и порядок в них часто обратный. Классификатор берёт `outcomes`, если это
имена, поэтому у winner-рынков сравнивались фамилия с полным именем (0.67 при
пороге 0.7 — мимо), а у тоталов, где `outcomes` это Over/Under и имена берутся
из заголовка, — полное имя с полным (1.0). Отсюда ноль связок типа
segment/winner при живом маппинге тоталов. Теперь у каждого участника набор
имён, вторая пара разворачивается по именам, а не по позиции, и к биграммам
добавлены два правила: общая фамилия (последний токен обязан совпадать, иначе
«MOUZ» и «MOUZ NXT» слились бы) и префиксная аббревиатура (NAVI ← Natus
Vincere).

**Единица счёта сверяется наравне с уровнем и типом.** `sameQuestion` сравнивал
только `level` и `kind`, поэтому матчевая фора в сетах вставала в пару с форой в
геймах, а тотал убийств — с тоталом раундов. Это второй, зеркальный дефект
маппинга: не пропущенная пара, а ложная, и она портит `dislocation_ratio`
молча. Теперь у обеих сторон есть ось `unit` (`kill`, `round`, `game`, `set`,
`map`), она сверяется только когда названа обеими сторонами (`Match O/U 23.5`
единицу не называет), и у победителей её нет.

**Справедливая цена берётся у второго токена того же рынка, а не у
букмекера.** У бинарного рынка два токена платят доллар на двоих, значит
`P(a) = 1 - P(b)`, а стоящее предложение продать `b` по 0.85 означает, что рынок
не оценивает `b` выше — то есть кладёт под `a` пол в 0.15. Бид, сметённый до
цента против такого пола, — это расхождение в 15 раз, выведенное из стоящих
заявок, а не предположенное. Оба токена подписывались с самого начала и обе
книги лежали в одной карте, так что это обошлось в одно обращение к Map.
Сшивка с gg.bet при этом остаётся: она отвечает на другой вопрос (что думает
букмекер), но у неё 2 заполненные строки из 2270, а у пары — почти все.

**Рынок, в котором торговал кошелёк, подписывается мимо дисциплин.** За одно
окно кошелёк сделал 113 филлов в 17 рынках, из которых наблюдались 2, а бейсбол
(47 позиций, второй вид по деньгам) не подписывался вовсе. Такой рынок теперь
берётся через CLOB и держится до резолюции независимо от дисциплины — это
покрывает бейсбол, не расширяя сканирование discovery, то есть ровно тот
размен, ради которого существует разделение `disciplines`/`labels`.

**Контекст филла пишется отложенно, а не в момент филла.** Филл не приходит
событием: он находится опросом журнала сделок через десятки секунд, а следующие
15 минут ещё не наступили. Поэтому филл ставится в очередь и описывается, когда
его горизонты прошли, из уже записанных снимков — той же механикой, что и
горизонты свипа. Держать снимки в памяти вместо этого — сотни мегабайт при
тысяче токенов и полная потеря при рестарте.

**Неполные позиции считаются с потолком, а не выбрасываются.** Позиция, где
продано больше, чем видно купленным, раньше исключалась из отчёта целиком —
отсюда расхождение с ручным пересчётом на $1022 и ни строчки об этом в отчёте.
Теперь продажи учитываются в порядке времени до объёма покупок, остаток идёт по
`payout_price`, позиция помечается `incomplete=1` и выводится отдельной строкой
плюс общий итог «с ними».

**Экспорт отдаёт сводки, а не сырые реестры.** Реестр из 13 тысяч рынков и
журнал вселенной из 51 тысячи строк давали 25.7 МБ, которые ни один чат не
прочитает. Сейчас — сводка по спорту и причине пропуска плюс только те рынки,
на которые ссылается остальной бандл: 29 КБ вместо 25.7 МБ.

**`pm-resolutions.csv` — сам себе кэш.** Закрытый рынок не меняется никогда,
поэтому повторный прогон резолвера трогает только незакрытые.

**Пять режимов выхода, а не два.** Позиция, проданная частично и оставленная
до резолюции, — это не «продано» и не «держали»: у неё есть и выручка, и
выплата. Смешивание портит и долю успеха, и кратности обеих групп.

**`isEntryPoint()` вместо сравнения строк.** См. §8, первый пункт.

## 7. Внешние API

### Gamma — `https://gamma-api.polymarket.com/markets`

Параметры: `active=true&closed=false&order=startDate&ascending=false&limit=100&offset=N`.
Возвращает массив рынков.

Подводные камни:
- **Страница ограничена 100** независимо от `limit`. `limit=500` молча вернёт
  четверть того, что кажется. Отсюда явная постраничная выборка.
- `clobTokenIds` и `outcomes` приходят **JSON-строками**, а не массивами
  (`parseJsonField`).
- Верхнеуровневого `eventSlug` нет — слаг лежит в `events[0].slug`.
- **Фильтр `condition_id` молча игнорируется** и возвращает нефильтрованный
  список. Это не ошибка запроса, а отравление данных: код, который поверит
  ответу, получит чужой рынок. Поэтому резолюция ходит в CLOB, где id — часть
  пути.

### CLOB REST — `https://clob.polymarket.com/markets/{condition_id}`

Отдаёт `question, market_slug, closed, end_date_iso, game_start_time,
minimum_tick_size, minimum_order_size` и массив `tokens` с `token_id`,
`outcome`, `winner`, `price`. Id в пути, поэтому подменить рынок невозможно.
Нет `events[]`, поэтому классификатору подсовывается `market_slug` — префикс
дисциплины в нём сохраняется (`cs2-color-btf-2026-08-25-game2`).

### CLOB WebSocket — `wss://ws-subscriptions-clob.polymarket.com/ws/market`

Подписка: `{ assets_ids: [...], type: "market" }` сразу после `open`.
Кадры:
- **Первый кадр после подписки — массив** снапшотов `book`, все последующие —
  одиночные объекты. Код, ждущий объект, потеряет весь стартовый срез.
- `book` — полная замена стакана, приходит периодически и ресинхронизирует.
- `price_change` — `{ asset_id, price, size, side }`, где `size` это **новый
  стоящий объём на этом уровне, а не дельта**; ноль убирает уровень.
- `last_trade_price` — принт, не событие книги, игнорируется.
- Простаивающий сокет закрывают: раз в 10 секунд шлётся текстовый `PING`,
  ответ приходит не-JSON и молча пропускается.

### Data API — `https://data-api.polymarket.com/trades`

`?market=<condition_id>&limit=500&offset=N&takerOnly=<bool>`, до 40 страниц.
Обход останавливается на короткой странице **и на странице, не добавившей
ничего нового**: проигнорированный `offset` иначе возвращает одну и ту же
страницу вечно. Оба случая помечают скан как `truncated`.

### Data API — `https://data-api.polymarket.com/activity`

`?user=<address>&limit=500&offset=N`. **Пагинация упирается в потолок около
5500 записей** — для активного кошелька это не полная история, и флаг `ceiling`
об этом говорит вслух. Своего id у записи нет, поэтому он собирается из
`transactionHash|asset|side|size|price`.

Общее для data-api: серия запросов ловит 429, **а иногда 400** — последнее
легко принять за кривой запрос. `politeFetch` ретраит статусы
`400, 408, 425, 429, 500, 502, 503, 504` и брошенные сетевые ошибки, с
удвоением паузы от 500 мс до 60 с; `throttle(350)` разносит запросы модуля.

### gg.bet — два GraphQL-вебсокета

- `wss://gg-b-gql.gg.bet/graphql` — линия и котировки;
- `wss://score-board.databet.cloud/graphql` — живое состояние.

Оба говорят конвертом `subscriptions-transport-ws`:
`{ id, type: "data", payload: { data: { <field>: ... } } }`.
`matches.sportEvents` — разовый снапшот, где `count` это общее число живых
матчей; `onUpdateSportEvent` — патчи, несущие id участников **без имён**;
`onUpdateSportEventOverviews.replace` — состояние по видам спорта.
Ключ сшивки: id gg.bet вида `5:<uuid>` против голого `<uuid>` у databet —
провайдерский префикс срезается (`normalizeId`).

### Что пробовали и отбросили

- **Прямой HTTP к gg.bet из США** — Cloudflare отвечает 403 «not accepting
  visitors from your region». Сбор идёт с машины пользователя.
- **Фильтр `condition_id` у Gamma** — молча игнорируется, см. выше.
- **Одна страница журнала сделок** — усечённый журнал читается как полный.
- **Полная выгрузка активности кошелька в базу** — 180 МБ мусора ради роли.

## 8. Известные проблемы и грабли

**Сравнение `import.meta.url` со строкой `file://` + `process.argv[1]` — молчаливый отказ.**
Node процентно кодирует URL (пробел → `%20`, кириллица, `#`) и разворачивает
симлинки, а `argv[1]` остаётся как есть. Достаточно пробела в пути к папке —
сравнение ложно, `main()` не вызывается, процесс выходит с кодом 0 без единой
строки вывода. Именно так `resolve.mjs` «ничего не делал». Теперь есть
`src/entrypoint.mjs::isEntryPoint()`, сравнивающий реальные пути. **Любая новая
точка входа должна использовать его**, а не сравнение строк.

**Убийство процесса по `pkill -f "src/pm/collector.mjs"`** попадает в
собственную командную строку и убивает вызывающую оболочку (exit 144, правки
«не применились»). Убивать только по PID.

**Два сборщика в одну базу.** Если случайно запустить `npm run pm` дважды,
обе копии пишут в один файл; диагностика становится ложью. Проверять
`ps aux | grep collector.mjs` перед стартом.

**`price_change` — это новый объём, а не дельта.** Прибавление вместо
присваивания даёт растущий из ниоткуда стакан.

**Первый кадр вебсокета — массив.** Уже описано в §7, но ошибка настолько
тихая, что стоит второго упоминания: теряется весь стартовый срез книг.

**Сон ноутбука.** `fetch` при потере сети не возвращает статус, а **бросает**
`TypeError: fetch failed`. Ретрай только по статусам означал, что закрытая
крышка убивала сборщик. Сейчас `politeFetch` ловит и брошенное; первый круг
discovery сделан нефатальным. `caffeinate` не спасает полностью.

**Список матчей gg.bet догружается скроллом.** `matches.count` говорит,
сколько матчей живо, а доставлено может быть меньше: страница подгружает
список лениво. `loadWholeList()` крутит до совпадения, `--rescan` (120 с)
повторяет. Строка `missing: <спорт> 12/28` в консоли — это про недокрут, а не
про отсутствие матчей.

**Патчи gg.bet приходят раньше снапшота с именами.** Пока матч не «разрешён»
(`resolved`), в CSV попадёт uuid вместо названия. `diffMatch` считает момент
разрешения началом матча (`match_start`), а не пачкой изменений.

**Одна и та же карта под дедуп CSV и под диффы рендера.** Из-за этого стрелки
изменения цены в консоли никогда не появлялись. Разделено на `recorded` и
`shown` — не сливать обратно.

**Тик у рынка не константа.** 0.01 и 0.001 сосуществуют; пороги детектора
поэтому в тиках плюс абсолютный пол.

**Детектор свипов до защит дал 617 281 срабатываний за день** по трём
причинам: пустая книга засчитывала все уровни; обвал начинался ниже цента;
одна пачка апдейтов писалась целиком. Защиты в `sweep.*`, снимать нельзя.

**`datetime(ts, '+5 minutes')` в SQLite возвращает не тот формат.** Ответ —
`2026-08-29 20:20:03`: пробел вместо `T`, без миллисекунд и без `Z`, тогда как
`ts` хранится как `new Date().toISOString()`. Сравнение строковое,
`'T' (0x54) > ' ' (0x20)`, поэтому `ts <= datetime(...)` было ложно **для
каждой строки за всю историю**. Так `high_1m/5m/15m` оказались пустыми во всех
5000 экспортированных свипах, и по той же причине была пуста секция payoff в
отчёте. Сдвигать границу теперь надо через `analyze.py::iso_shift`, который
отдаёт ровно тот формат, в котором хранится `ts`.

**`query()` возвращает по строке на каждый дневной файл.** Он выполняет запрос
во всех базах диапазона и склеивает результаты, поэтому у
`ORDER BY ts DESC LIMIT 1` результатов столько, сколько файлов, а `rows[0]` —
это самая свежая строка **самого старого** дня. Для свипа с последнего дня
контекст брался за несколько суток до события, молча. То же с `max(...)`:
агрегат приходит по одному на файл. Есть `newest(rows)` и `highest(rows)`,
пользоваться надо ими.

**Позиционный `INSERT INTO ... VALUES (?,?,...)` и добавленная колонка.**
Дневные файлы создаются через `CREATE TABLE IF NOT EXISTS`, поэтому база,
открытая после добавления колонки, остаётся в старой форме. `markets` и
`sweeps` переведены на явные списки колонок, а `Store` при открытии
доделывает недостающие через `ALTER TABLE ADD COLUMN` (`COLUMN_ADDITIONS`).
Любая новая колонка должна попадать и в схему, и в этот список.

**`gameStartTime` приходит не в ISO.** Формат `2026-09-01 07:30:00+00`: пробел
вместо `T` и двузначное смещение. Прочитанное как локальное время это сдвинуло
бы всё окно подписки на смещение машины, молча. Разбирать только через
`schedule.mjs::parseTimestamp`.

**`datetime.fromisoformat` до Python 3.11 не принимает смещение `+00`.**
А CLOB отдаёт `game_start_time` именно так: `2026-09-01 07:30:00+00` — пробел
вместо `T` и две цифры вместо четырёх. На 3.11 это парсится, на 3.10 бросает
`ValueError`, и под перехватом исключения поле молча выходило пустым на одной
машине и заполненным на другой. Так пропал `minutes_from_game_start` у всех
рынков, датированных из `pm-resolutions.csv`. Разбирать время только через
`analyze.py::parse_timestamp`: он нормализует строку **до** передачи в
`fromisoformat` (смещение к виду `+HH:MM`, доли секунды к 3 или 6 знакам),
поэтому работает одинаково на 3.10 и 3.13. Проверять правки надо на 3.10 —
на 3.11 такая ошибка не воспроизводится.

**`resolved_before_horizon` был недостижим, а не сломан.** Опрос резолюции
начинался через 45 минут после начала матча, а горизонты закрываются через 1, 5
и 15 минут после свипа. К моменту первого вопроса все горизонты уже записаны с
нулём — отсюда ноль во всех 2270 строках. Теперь рынки с открытым горизонтом
опрашиваются раз в минуту отдельно от общего расписания. Стопроцентного
заполнения не будет никогда: CLOB объявляет рынок закрытым не мгновенно.
Основной сигнал «рынок умер» — это `book_frozen`, он считается при записи и ни
от чего не зависит.

**`levels_crossed` почти всегда равен единице, и это правда.** Считаются уровни,
стоявшие **выше нового лучшего бида**, а типичная книга здесь двухуровневая:
мейкер на тридцати центах и биды по центу-два, между ними пусто. Снесли один
уровень — получили единицу. Порог `sweep.levelsCrossed` тут ни при чём, он решает
только, писать ли свип. Информацию несут добавленные `levels_touched` (включая
уровни, которые похудели, но остались) и `size_eaten_partial`.

**Журнал активности кошелька отдаёт историю, а не новости.** Первый же опрос
возвращает тысячи записей за прошлые месяцы. Без ограничения по свежести
(`wallets.followHours`, `fillContext.maxAgeHours`) это заливает и подписку, и
таблицу контекстов давно неактуальными рынками.

**Колонка, посчитанная и сохранённая, ещё не колонка в бандле.** Три отчёта
подряд приходили с ответом «данных нет» на один и тот же вопрос, потому что
`export.py` собирал `sweeps.csv` по фиксированному списку из 32 имён, написанному
до появления парных колонок, а строку строил позиционно под этот список. Запрос
возвращал `SELECT s.*` со всеми колонками, лишние молча выбрасывались при записи.
Теперь список объявлен рядом с кодом, который его наполняет (`SWEEP_COLUMNS`),
строки собираются словарями, а `write_csv` падает с `SchemaError`, если ключи не
совпадают с заголовком **в любую сторону**. Лишний ключ — ошибка ровно так же,
как недостающий: именно лишний и терялся.

**Пустая колонка «до» у входа — это чаще всего охват, а не поиск.**
`Store.bookAt` берёт ближайшую предшествующую строку без всякого окна, а у
колонок `*_before` фильтра свежести нет. Пусто — значит строки книги до филла в
базе нет вообще. Так бывает по двум причинам, и путать их нельзя: рынок был вне
`disciplines` и попал в расписание через сам филл (лечится только охватом), или
рынок был в охвате, но слот ушёл другой дисциплине (лечится квотами). Мерить
долю надо по рынкам, подписанным **раньше** филла, — иначе метрика показывает
0% и читается как поломка лукапа, которой нет.

**`sqlite3.Row` не имеет `.get()`** — нужен `dict(row)`.

**Node игнорирует `HTTPS_PROXY`** во встроенном `fetch` без
`NODE_USE_ENV_PROXY=1`.

**`export.py` брал отчёт по позициям только из корневого `target-fills.csv`.**
На машине, где такого файла нет, бандл молча уезжал без PnL. Исправлено:
берётся тот файл, который есть, корневой в приоритете.

**`.gitignore` глушит `*.csv` и `data/`.** Собранное **не** попадает в git и
существует только на машине сбора. Исключение — `samples-pm/*.csv`. Перед
переустановкой машины данные надо копировать руками.

**`package.json` engines говорит `>=20`, а нужен Node 22** (`node:sqlite`).

## 9. Что осталось недоделанным

- **Данные за 25–29 августа собраны со сломанным окном подписки.** Ни один
  филл целевых кошельков не попал внутрь наблюдавшегося окна своего рынка
  (0 пересечений по 358 токенам), медиана наблюдения 61 минута за сутки до
  игры. Свипы в них реальны, но это свипы рынков **до матча**, а не во время
  него; связывать их со сделками кошельков нельзя. `high_*` и контекст на этих
  данных теперь считаются задним числом (правка формата границы), а вот
  пересечения с филлами не появятся — их там нет.
- **Покрытие маппинга gg.bet не измерено.** Правки матчера покрыты юнит-тестами
  на реальных парах имён, но сквозной замер «какая доля связок — победители
  сегментов» требует прогона, где оба сборщика работают одновременно:
  фикстуры `samples-pm/` содержат непересекающиеся матчи (лучшая пара имён
  между ними — 0.23). Проверять по `python3 check.py`, строка про
  segment winners. Отдельно стоит убедиться, что gg.bet вообще отдаёт
  «Карта N - победитель» для нужных дисциплин:
  `cut -d, -f8 odds-history.csv | sort -u | grep -i победител`.
- **Данные за 25 и 26 августа непригодны для статистики свипов.** 535 400
  записей из 648 364 — это 26-е, когда детектор считал одно схлопывание заново
  на каждом апдейте. Частота: 2.54 и 9.41 события на рынок-час против 0.31–0.49
  после защит. Решение «выкинуть эти два дня» принято, но **в коде не
  зашито** — `analyze.py --since 2026-08-27` надо передавать руками.
- **У 25 и 26 августа нет таблиц `universe` и `trade_scans`** — они появились
  позже. Воронка «рассмотрено → подписано» для тех дней не считается вообще.
- **`mapping.csv` никто не верифицировал руками.** Все строки — предложения
  матчера с `verified=0`. «NAVI» против «Natus Vincere» даёт 0.29 по биграммам,
  и порогом это не лечится. Сшивка работает, но её точность не подтверждена.
- **`unsubscribed_at` заполняется, когда расписание отпускает рынок** — по
  резолюции, по истечении `holdHours` или потому, что окно прошло, пока
  сборщик был выключен; причина лежит в `markets.release_reason`. Если
  сборщик остановлен раньше, поле останется NULL — это по-прежнему не признак
  живого рынка.
- **Личный fill rate кошелька не измерим в принципе.** Неисполненные заявки и
  отмены не существуют ни в блокчейне, ни в публичном фиде CLOB. То, что
  считает `analyze.py`, — это «как часто книга вообще проваливалась до 1–2
  центов», верхняя оценка, а не его частота исполнения. Это ограничение
  данных, а не недоделка кода, но следующий чат обязан о нём знать.
- **Выборка мала.** Пять дней, 358 позиций. По Dota 19 наблюдений, по Valorant
  24, в режиме `held_won` 13. Разрезы по дисциплинам статистически пусты.
- **`export.py` кладёт в бандл не больше 5000 значимых свипов**
  (`--max-sweeps`), потому что контекст каждого события стоит отдельного
  обращения к `book`. Выборка теперь стратифицирована по дням с равными
  квотами, реальные размеры страт лежат в `sweeps-strata.csv`, а диапазон дат
  выборки написан в шапке бандла. Частоты всё равно надо брать из `report.txt`
  и `coverage.csv`: 5000 из 117 616 — это выборка, а не перепись.
- **Две стратегии в одних данных.** 316 позиций входят дешевле 0.05 и 41 —
  по 0.84–0.90, причём вторая группа держит 70% капитала. Разделение сделано
  в отчёте, но всё остальное (свипы, fill rate) считается как будто стратегия
  одна.
- Второй прогон `export.py` в конвейере — костыль: скрипт не умеет сам
  сходить за резолюциями. Работает, но порядок команд приходится помнить.
- **`resolved_before_*` полностью заполнить нельзя.** CLOB объявляет рынок
  закрытым с задержкой, а горизонты закрываются через 1, 5 и 15 минут. Рынок,
  который успел рассчитаться внутри горизонта, всё ещё может стоять с нулём.
  Опрос рынков с открытым горизонтом раз в минуту это сузил, но не убрал.
  Признак «книга умерла» брать из `book_frozen`: он считается при записи, из
  собственных часов книги, и ни от какого внешнего ответа не зависит.
- **Эффект `schedule.maxLivePerSport` на реальных данных не измерен.** Потолок
  в 150 выбран по прошлым числам (теннис 842, CS2 582) и должен увести долю
  крупнейшей дисциплины примерно к 30%. Проверять после суток сбора по
  `check.py`, строка «the largest discipline is N% of M deep sweeps»; критерий
  — не больше 40%. Побочный эффект — база примерно втрое меньше, и это
  сознательный размен объёма на сравнимость.
- **Кошелёк торгует там, куда discovery не ходит, и решение по охвату не
  принято.** По сбору 02–04 сентября все 1883 филла принадлежат одному адресу
  (`0xd403…`); второй настроенный адрес (`0x8840…`) не дал ни одной сделки и
  с 5 сентября из конфига убран.
  Разбивка по дисциплинам: CS2 499, теннис 426, **бейсбол 376**, LoL 357,
  Dota 97, Valorant 70. Бейсбол не историчен — последний филл 4 сентября, самый
  свежий из всех дисциплин; за сентябрь 39 из ~340. При этом `baseball` лежит в
  `labels`, а не в `disciplines`, то есть discovery такие рынки не ищет и они
  попадают в расписание **только через уже случившийся филл** (`followWallets`,
  лаг 9–20 секунд от сделки до первой строки книги). Для них колонки `*_before`
  в `fill_context` не заполнятся никогда — это граница метода, а не баг.
  Варианты: перенести `baseball` (и, возможно, `basketball`) в `disciplines`,
  либо оставить охват и читать покрытие по BUY как исключающее их. `check.py`
  теперь сам печатает долю филлов вне сканируемых дисциплин с порогом 10%.
- **`book-series.csv` покрывает только 300 самых глубоких свипов**
  (`--series-sweeps`), окно −5…+15 минут, один снимок в 30 секунд. Таблица
  `book` бьётся heartbeat'ом раз в 5 секунд на токен, и полный её экспорт —
  ровно то, ради чего бандл существует.

## 10. Как проверить, что всё работает

### Тесты

```bash
npm test
```
22 набора на Node плюс `test_analyze_fills.py`, `test_export.py` и
`test_bundle.py` — 25 строк `all ... tests passed` и код возврата 0. Строка `write to test.csv failed:
disk full` — это специально проверяемый случай в `appender.test.mjs`, не сбой.

### Состояние сбора

```bash
python3 check.py
```
Ожидаемо на здоровом сборе: `20 ok, 5 warnings, 0 missing`.
Любой `[ MISS ]` — блокирующий. Пять законных предупреждений:

| Предупреждение | Почему оно нормально |
|---|---|
| `pm-2026-08-25.sqlite predates trade_scans, universe` | таблицы появились позже; задним числом не заполнить |
| то же про `2026-08-26` | там же |
| `N disconnects totalling M minutes` | честная запись невидимых окон, вычитается из знаменателя |
| `N significant sweeps is not a count of events` | напоминание смотреть на частоту по дням, а не на сумму |
| `1 positions have incomplete history` | покупки были до старта сбора |

Признаки поломки: `no rows for N of the five disciplines` (сборщик запущен без
части спортов), `the universe journal is empty`, `no sweeps logged`,
`X/Y traded markets have an outcome` ниже 90%, любой `[ MISS ]`.

### Окно подписки — секция `== the subscription window ==`

Отдельная секция `check.py`, отвечающая на вопрос «смотрели ли мы игру».
Пороги:

| Строка | Порог | Что означает провал |
|---|---|---|
| `N/M markets (X%) were watched during their match` | ≥ 80% | расписание не срабатывает; всё остальное считать бессмысленно |
| `N/M sweeps have a 5-minute high recorded` | ≥ 90% | горизонты не дописываются; `export.py` добирает их из снапшотов |
| `N/M sweeps carry a gg.bet fair value` | ≥ 20% | сборщик gg.bet не работал или его матчи не те |
| `N/M mappings are segment winners` | ≥ 50% | маппинг ловит тоталы, а кошельки торгуют победителей сегментов |
| `coverage.csv carries gap_seconds` | есть | разрывы не вычитаются, все частоты на час завышены |
| `N/M sweeps carry a fair value from the twin token` | ≥ 90% | у второго исхода не было аска, пол под цену не подставить |
| `N/M sweeps have a twin quote under 30s old` | ≥ 70% | пол взят из книги, которую никто не трогал минутами |
| `N/M wallet fills have the book around them` | ≥ 40% | филлы идут в рынках, за которыми не следят — приоритет по кошельку не срабатывает |

Строка `N markets are scheduled for a match that has not started` — это норма,
такие рынки в знаменатель первой строки не входят.

### Что видно в базе напрямую

```bash
sqlite3 data/pm-$(date -u +%F).sqlite \
  "SELECT trigger, count(*) FROM book GROUP BY trigger;"
```
Должны быть все три: `heartbeat` заметно больше остальных, `book` и `change`
ненулевые. Отсутствие `change` означает, что живёт только таймер, а поток
обновлений не идёт.

```bash
sqlite3 data/pm-$(date -u +%F).sqlite \
  "SELECT role, count(*) FROM trades GROUP BY role;"
```
На известных данных — `maker` и ноль `taker`. Появление тейкерских филлов у
целевых кошельков будет означать смену их поведения, а не ошибку.
